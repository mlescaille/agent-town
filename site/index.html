          01
          
An agent has to say who it is

          
Who is speaking, on whose behalf, and what it is about to do. An agent does not mint that authority. A separate issuer signs a license that names the agent, the user it acts for, how it was delegated, and what it may do.

          
At a checkpoint outside the agent, every call brings that license and a justification the agent signs for this call: why this call, on whose behalf, is the one being made. The justification lives at most 300 seconds. The checkpoint remembers its id and rejects a replay.

          
The checkpoint checks the signature, the lifetime, the scope, the delegation chain, and the mandate. It asks a Cedar policy over the OpenID AuthZEN 1.0 evaluation API. It appends the decision, allow or deny, to a tamper-evident log. It forwards the call only if the decision is allow.

          
This repository is a prototype of that flow. It is not a production trust service. The services bind to localhost and share a key directory.

        

        
    
          
  • The issuer signs licenses. Agents never do.
    • 
          
  • Signatures are Ed25519 JWS. No other algorithm is accepted.
    • 
          
  • A license carries exactly one mandate.
    • 
          
  • A sub-agent can receive only a narrower license. Scope, budget, and expiry can shrink. They cannot grow, and the mandate type cannot change.
    • 
          
  • The chain is an RFC 8693 act claim, at most eight agents, with no repeated id. The outermost actor is the agent presenting the license.
    •

        02
        
Three mandate types

        
A license carries exactly one. The justification’s basis has to match it. A call inside the scope is still denied when the basis claims a different kind of instruction than the user signed.


        

          

            
direct_request

            
          

          
The user asked for one exact action and one location. The authorization detail contains only that pair. The checkpoint allows a call only when both match. The justification basis must be user_request. A goal on the justification is rejected.

          
The sample names calendar.read on calendar:primary, with max_calls=1.

        


        

          

            
user_goal

            
          

          
The user set a goal, one to 300 characters. The agent chooses calls inside the granted scope. The justification basis must be user_goal, and the goal text must equal the mandate. Claiming user_request is justification_mismatch: the user did not ask for that exact action.

          
The sample goal is “Summarize the primary calendar”, with calendar.read and calendar.create on calendar:primary, budget 10.

        


        

          

            
agent_initiated

            
          

          
The user signed a grant that lets the agent act without a goal. The scope has to sit inside a fixed ceiling, and max_calls has to be present and at most 5. The justification basis must be agent. A goal is a mismatch. Cedar’s forbid-agent-initiated-writes forbids a write. The effect comes from the action name: read, list, and get are reads. Every other verb is a write.

          

            Ceiling for an agent_initiated license
            
              
ActionLocation

            
            
              
catalog.listcatalog:public

memory.readmemory:self

            
          

          
The sample is inside that ceiling: clock.read on clock:local, max_calls=3.

        


        

          

            
Attenuation, not a fourth mandate

            
          

          
The issuer verifies the parent and signs the child. The parent agent does not. The child copies the user, the mandate, the transaction id, and the request hash. It sets parent_jti and nests act. Every child action and location is already in the parent. The budget cannot rise, and the expiry cannot move later. At least one of those has to be strictly narrower. Adding mail.send is scope_widen.

          
The sample child keeps the calendar goal, drops calendar.create, lowers the budget from 10 to 3, and shortens the lifetime. The presenter is researcher.

        

      

    


    

      

        03
        
How a check works

        
License, then checkpoint, then policy, then the log. The tool is called only after an allow is written down.

        
    
          
  1. 
            01 License
            
    The call brings a license
    
            
    The caller posts the tool call to /v1/invoke with headers Agent-License and Agent-Justification. licensed(fetch) attaches both. The URL you pass it is not contacted.
    
          
    2. 
          
  2. 
            02 Checkpoint
            
    Outside the agent
    
            
    The checkpoint verifies the license and the justification, including scope, chain, mandate, and budget. A structural failure is reported even if Cedar would also have denied. No license is missing_license.
    
          
    3. 
          
  3. 
            03 Policy
            
    AuthZEN, then Cedar
    
            
    permit-bound-call permits a call only when the checkpoint’s booleans are all true. forbid-direct-request-inexact forbids an inexact direct request. The default is deny. If the policy decision point cannot be reached, the checkpoint fails closed.
    
          
    4. 
          
  4. 
            04 Log
            
    Then the tool, or not
    
            
    Allow or deny, the decision is appended first. The log is an RFC 9162 Merkle tree with SHA-256, and it signs each tree head. Only an allow is forwarded.

        05
        
The format, and the repository

        
The byte-level rules for the license, the justification, and the log are the v1 profile. It borrows names from existing specifications. It is not itself an IETF standard.

        
    
          
  • spec/LICENSE-FORMAT.md
    • 
          
  • policies/mandates.cedar
    • 
          
  • ROADMAP.md
    • 
          
  • Repository
    • 
          
  • Pull request #1, explicit delegation chain
    • 
        

        
packages/core holds the types, the Ed25519 JWS, attenuation, the checkpoint rules, and the Merkle tree. packages/cli is the agentlicense binary. packages/sdk is licensed(fetch). services/issuer, services/checkpoint, services/pdp, and services/log are the four local processes. examples/demo is the scripted walkthrough.

      

    


    

      

        06
        
Next is an MCP gateway

        
The checkpoint in v1 is an HTTP proxy in front of one tool API. The next milestone is a gateway in front of Model Context Protocol servers. v1 proves the token, the policy call, and the log. It does not speak MCP.

        
    
          
  • tools/call is refused unless the caller presents a current license and a fresh justification.
    • 
          
  • tools/list is filtered to the tools named in authorization_details.
    • 
          
  • When an agent spawns a sub-agent, the gateway asks the issuer to attenuate the license before the child receives it. The child cannot be given a tool the parent license does not already grant.
    • 
          
  • Each allowed or denied tools/call is appended to the same Merkle log, with the MCP server name and tool name as the action and location.
    • 
          
  • The gateway stays outside the agent process, as the checkpoint does today.
    • 
        

        
After that: enrollment without a shared directory, revocation before exp, budgets that survive more than one checkpoint process, a required user-request JWS, ancestor scopes a checkpoint can re-check, a witness for the log, and authenticated calls to the policy decision point.

        

          
Limits of this prototype

          
The issuer is the only signer, so a checkpoint cannot re-prove that an ancestor scope was narrowed unless it is shown the parent license. The policy decision point trusts the checkpoint’s booleans (in_scope, basis_ok, and the rest) and is meant to stay on localhost. Budgets live in the checkpoint process. The log key can rewrite history if an observer did not keep an older signed tree head.

          
v1 copies the mandate through attenuation. Whether a goal should be allowed to narrow into one exact action is an open question in the roadmap, along with four others. The code picks one side so the prototype runs.
